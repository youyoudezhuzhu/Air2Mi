# Air2Mi Plus：应用与内核授权分工

fnOS 0.1.7 在侧栏提供“授权与购买”页面，手机端从顶部 Plus 入口打开。页面可读取本机授权、实例配额和设备码，也可提交激活码、在线校验或按设备码恢复。设置页保留授权摘要。

激活码转给内核，由内核联网、验证固定
Air2Mi Ed25519 公钥签名、绑定 AMD1、加密保存凭证，决定是否允许超过两个 AirPlay 实例。
App 不存 CDK、不维护第二套授权判断，不内置 Engine/授权凭证。

fnOS Go Host 代理 `/v1/license` 和 activate/restore/validate，遵循原管理员、CSRF、
本地 token 边界。旧 Engine 没有接口时显示“当前内核未提供可用授权接口”，不显示虚假授权。
Android 复用同一 Vue 组件，Host 提供 ANDROID_ID 并给联网操作预留 15 秒本地读超时。
需要单独导入具备此 API 的 Android Engine；本次 APK 不会包含该组件。

fnOS 的 `/api/plus/offers` 从固定授权服务读取公开商品配置，缓存 60 秒并支持 ETag。内核停止时仍可查看商品。`OFFER_NOT_CONFIGURED` 显示为尚未上架，网络故障显示为暂不可用。只在 enabled 和 purchasable 严格为 true、
purchase_url 为 HTTPS、button_text 有效时展示购买入口；系统浏览器打开，价格来自 price_minor/currency。
商品配置不能解锁内核。

0.1.9 页面显示和复制均使用 AVD1 展示码；真实 AMD1 继续由 Engine 用于激活及恢复。展示码可逆，按敏感数据处理。
不要把完整码/卡密/凭证放进截图、日志、公开工单。只收集用户主动输入的激活码，不做本地持久化。

完整购买流程依赖服务端上架商品。用户自行解绑和换机由销售渠道处理。

## 对照 PushMi 的接入审查（0.1.8）

PushMi 的 PVD1 展示码是将真实 PMD1 的 16 字节与固定 SHA-256 掩码异或，客服工具可以反算。它降低直接展示真实码的频率，公开算法仍然使展示码能够反算真实码。支持仅凭设备码恢复授权时，两种码都需要按敏感信息处理。

0.1.8 审查时，Air2Mi 交接契约将 AVD1 标为尚未启用，当时采用默认折叠 AMD1、用户主动复制的方式。0.1.9 按用户要求启用 AVD1 展示，详情如下。

对照发现商品数据只校验应用及商品标识，`button_text` 等字段的异常类型可能使前端购买区域报错。0.1.8 在 Host 与 Web 校验 schema_version、布尔开关、币种、金额、文字及权益字段；不符合契约时显示购买信息异常，已有授权仍由 Engine 判断。回归覆盖异常商品不能进入缓存，以及后续有效响应可以恢复。

公开商品接口在本轮检查时仍返回 `OFFER_NOT_CONFIGURED`。需要由商品后台配置 Air2Mi 的价格、权益和 HTTPS 购买链接，完整付款流程才能联调。

PushMi 启动时还会进行受节流保护的后台授权复核。当前 Air2Mi 内核的在线检查由管理 API 显式触发，应用提供“联网检查 / 恢复授权”。若需要自动发现服务端撤销，需要另行在 Engine 生命周期中增加受节流保护的后台检查，并继续遵循网络错误保留有效凭证、明确撤销才锁定的约定。

## AVD1 展示码（0.1.9）

授权页只显示和复制 AVD1，不再提供显示真实 AMD1 的按钮。设备身份及授权绑定继续使用原来的 AMD1，前端转换只用于展示。

算法取 `SHA-256("air2mi.device.display.v1")` 的前 16 字节，得到 `3A69EA0374CC555A6EC103FCDF39B012`，与真实设备码的 16 字节异或，再按四位十六进制分组并加 `AVD1-` 前缀。异常输入显示不可用，不回退展示真实码。

客服可在可信本机运行 `python3 tools/device_display_code.py <AVD1>` 还原 AMD1；反向使用 `--encode <AMD1>`。服务端及机器人如需直接接受 AVD1，需要复用此转换。本轮没有修改授权服务，激活与恢复请求始终由 Engine 自动携带 AMD1。

AVD1 使用公开可逆算法，拿到完整展示码仍可反算真实码。仅向可信授权支持渠道提供。

## 用户侧 API 出口（0.1.10）

fnOS Host 在面向浏览器返回响应前，将 AMD1 转换为 AVD1。覆盖授权查询和激活/校验/恢复结果、普通 JSON、错误文本、日志、诊断及 SSE。应用 API 中的 `device_id` 是展示码，前端直接显示和复制该值。Engine 的私有 API 与服务端授权请求继续使用真实码。

响应适配不会修改授权状态、配额或 Engine 存储。JSON 转义先规范化再过滤，数值使用 json.Number 保留大整数；流式事件按行处理跨网络读取拆分的设备码，并将关闭操作传给原始流。

此出口规则减少应用接口暴露真实码的机会。固定公开 XOR 掩码仍可被反算，也无法对持有设备管理权限、能读取本地运行时或逆向程序的人隐藏所有内部数据。若需要展示码本身无法被用户还原，需要另行采用由服务端持有私钥的方案及相应服务端协议。

## 授权页面顺序（0.1.11）

按 PushMi `Ui2PlusScreen` 整理为商品信息、已激活状态、当前设备识别码、激活详情的单列页面。激活码使用弹窗输入，提供粘贴、清除和格式提示；已激活时购买和重新输入激活码需要确认。价格、权益、AVD1 和授权状态来自现有接口。

移除原页面的配额统计、签发时间、步骤说明、常见问题和技术诊断说明，保留 Fluent 浅色视觉。0.1.11 时 Engine 尚未提供清除本机授权接口，该操作在 0.1.12 接通。

## 清除本机凭据（0.1.12）

使用 Engine beta.8 的 `POST /v1/license/clear`，Host 继续检查管理员权限、CSRF 和内核私有 token。只有内核状态返回 `can_clear: true` 时，已激活卡片才显示“清除本机授权凭据”。确认框提供“保留授权”和“清除凭据”。

清除会停止数据面并删除本机授权凭据，服务器绑定和用户配置保留。授权页可继续恢复授权；如果恢复或激活成功时数据面处于 stopped，应用通过已有生命周期接口重启 Engine，让保存的接收器重新上线。旧 Engine 的状态和其他操作仍可使用。
